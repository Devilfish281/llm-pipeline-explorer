# ADR 0002 — Stabilize Python Transformer Training and Process Lifecycle

**Status:** Accepted

The Python Backend will preserve the reference decoder-only Transformer architecture and educational behavior while replacing host-dependent TypeScript process behavior with a stable Python-owned contract.

The fixed Transformer Training Corpus is converted into one immutable, lazily initialized Transformer Preprocessing Snapshot. Initialization uses a module-local `threading.Lock`, publishes only a completely built and validated snapshot, and permits a later retry after failure. Every valid request starts from fresh request-owned Mulberry32 seed `42` and uses NumPy `float32` weights, activations, gradients, and optimizer buffers. The architecture fixes context length `32`, embedding dimension `32`, two heads, feed-forward dimension `128`, and training-sequence length `16`; only the requested one-through-six layer count varies.

One stable weight-layout builder is the sole authority for parameter ordering, float offsets, lengths, shapes, and total parameter count. It preserves this order: `tokEmb`, `posEmb`; then for each block `ln1Gamma`, `ln1Beta`, `wQ`, `bQ`, `wK`, `bK`, `wV`, `bV`, `wO`, `bO`, `ln2Gamma`, `ln2Beta`, `ff1W`, `ff1B`, `ff2W`, `ff2B`; then `lnFGamma`, `lnFBeta`, `headW`, and `headB`. Parent and worker NumPy views use `float32`, C order, and `byte_offset = float_offset × 4`. The same layout controls shared-memory interpretation, Xavier initialization order, gradient buffers, Adam traversal, `totalParams`, and Saved Transformer Model reconstruction.

The Python forward and backward implementations preserve the reference mathematical formulas, tensor shapes, causal mask, layer-normalization behavior, attention-head splitting and concatenation, residual connections, feed-forward activation, cross-entropy calculation, backward dependencies, parameter order, and `float32` stored numerical state. They are not required to reproduce every TypeScript scalar loop or every floating-point accumulation in identical order. Carefully selected NumPy matrix and reduction operations may be used to provide practical Python performance. Consequently, hidden unrounded numerical values are verified with explicit tight tolerances rather than a universal bit-for-bit TypeScript-equivalence promise.

Each request owns one flat shared weight block and four flat shard-gradient blocks. Adam moments and the Ordered Gradient Reduction workspace remain parent-local. Training Sequences are divided into four contiguous Logical Training Shards using `ceil(sequence_count / 4)`. The actual worker count is calculated once as `min(4, max(1, os.cpu_count() or 1))`; shards are assigned through `shard_id % actual_worker_count`. Workers are spawned through a request-local `"spawn"` multiprocessing context, receive read-only weight views, and write only to their assigned shard-gradient blocks. The parent alone reduces shard losses and unaveraged gradients in order `0 → 1 → 2 → 3` and applies one Adam update per inclusive epoch using learning rate `0.001`, beta values `0.9` and `0.999`, epsilon `1e-8`, and step `epoch + 1`. No gradient averaging, clipping, weight decay, schedule, sequence shuffling, or early stopping is introduced.

Each worker has a dedicated duplex pipe using typed `ready`, `compute`, `result`, `failure`, `stop`, and `stopped` messages. Epoch and shard identities are validated; stale, duplicate, missing, malformed, unassigned, or non-finite results fail the run. Worker pipes and process sentinels are polled in `0.1`-second waits through `asyncio.to_thread()`, with browser-disconnection checks after every poll.

Progress uses `max(1, floor(epochs / 50))`, includes epoch zero and the exact final epoch, and attaches one Generated Text Sample to every Transformer Epoch Update. Each sample uses an independent Mulberry32 stream seeded with `(42 + epoch) modulo 2³²` and otherwise preserves the reference temperature and top-p generation algorithm. Generation and final-loss evaluation run through `asyncio.to_thread()` and support cooperative cancellation between tokens or Training Sequences.

The route validates the exact five-field request contract, acquires one process-local run lock nonblockingly, and prepares preprocessing and the exact eleven-field `init` payload before returning `StreamingResponse`. Validation failures return HTTP `422`, overlaps return HTTP `429`, and preprocessing failures return a sanitized HTTP `500`. The first streamed event is `init`; successful streams then emit approximately fifty `epoch` events and exactly one `done`.

After the last Adam update, final loss is recomputed from the final weights. One complete named JSON model is atomically persisted as `transformer-weights-e{epochs}-l{numLayers}-d32-h2-ff128-ctx32.json`. Only after persistence succeeds is `done` emitted with exactly `architecture`, six-decimal `finalLoss`, and ordered `samples`. Saved models are retained per training configuration but are never loaded as caches, resume points, or shortcuts.

Disconnects and post-stream failures terminate quietly without persistence, `done`, a new SSE `error` event, or exposed internal details. Cleanup requests cooperative worker shutdown, waits up to two seconds, terminates remaining workers, waits two additional seconds, and kills any worker still alive. Workers are joined and process and pipe objects are closed before shared memory and the run lock are released. Forced termination always marks the run unsuccessful.

Transformer verification uses a two-level numerical comparison policy. Discrete structures, deterministic random sequences, layouts, ordering, worker assignments, protocol identities, reporting boundaries, SSE field sets, generated samples, six-decimal public values, and six-decimal serialized model contents use exact comparisons against independently produced fixtures. Unrounded activations, logits, attention values, normalization outputs, gradients, shard losses, Adam buffers, updated weights, and final loss use explicitly selected tight relative and absolute tolerances. Tests use strict shape and `float32` dtype checks where applicable. No tolerance may be broadened merely to make a failing formula, layout, reduction-order, or dtype test pass.

Every publicly streamed or persisted Transformer number specified as six-decimal uses one TypeScript-compatible rounding helper. The helper rejects non-finite inputs, multiplies the value by `1,000,000`, chooses the nearest integer with exact halfway cases resolved toward positive infinity, divides by `1,000,000`, and normalizes either signed zero result to positive `0.0`. Python’s built-in `round()` is not used at this compatibility boundary. The helper applies to Transformer Epoch Update losses, final loss, every persisted model weight, and any future Transformer field explicitly defined as six-decimal.

Saved Transformer Models use one deterministic JSON serialization contract. The complete model is serialized in memory using `json.dumps()` with two-space indentation, `ensure_ascii=False`, `allow_nan=False`, and `sort_keys=False`, followed by exactly one newline. All dictionaries are constructed in their canonical persisted order: top-level `type`, `config`, `vocab`, `merges`, and `weights`, followed by each nested configuration and named-weight field in its established reference order. Serialization must finish successfully before a temporary destination file is created. Any unsupported value, non-finite number, serialization error, or key-order defect fails persistence and prevents `done`.

Final Saved Transformer Model persistence uses a secure same-directory temporary-file replacement boundary. After deterministic JSON serialization completes in memory, the backend creates the `.data` directory if necessary and securely creates a unique temporary file there using `tempfile.mkstemp()`. It writes UTF-8 text with explicit `\n` line endings, flushes the Python buffer, calls `os.fsync()` on the open file descriptor, closes the temporary file, and replaces the configuration-specific destination using `os.replace()`. Any failure before successful replacement removes the temporary file where possible, preserves the previous destination, prevents `done`, and marks the run unsuccessful.

Saved Transformer Model persistence ends after the completed temporary file has been flushed, synchronized with `os.fsync()`, closed, and successfully moved to the configuration-specific destination using `os.replace()`. Phase 5 does not require a separate directory synchronization after replacement because the supported Windows-first backend needs one portable persistence contract. This boundary prevents intentional exposure of partially written JSON but does not claim the strongest possible directory-entry crash durability available through platform-specific POSIX operations.

Production Saved Transformer Model paths are resolved from the installed backend module location rather than the process working directory. The Transformer model-directory resolver derives the backend project root from `Path(__file__).resolve().parents[3]` and appends `.data`. Starting Uvicorn from a different PowerShell directory therefore cannot redirect model persistence. Tests may explicitly inject a temporary destination directory, and no production path contains a user-specific absolute filesystem location.

The parent process is the sole creator and unlinking owner of the five request-scoped shared-memory blocks. Python generates each block’s unique name, and the parent passes only those names, expected byte sizes, canonical layout metadata, and shard assignments to spawned workers. Workers attach with `create=False`, construct their NumPy views, and close every attached handle in a guaranteed `finally` boundary after releasing references to the views. Workers never call `unlink()`. After every worker has exited and been joined, the parent closes its own handles and invokes `unlink()` exactly once for each block. Attachment, size-validation, close, or unlink failures are logged internally; they never expose implementation details through SSE.

Each spawned worker sends `ready` only after completing its startup boundary. It must attach to all five request-scoped shared-memory blocks, validate their required capacities and the complete canonical parameter layout, construct C-contiguous `float32` NumPy views, mark all weight views non-writeable, and expose writeable gradient views only for its assigned Logical Training Shards. The layout must begin at float offset zero, contain no gaps or overlaps, use positive lengths whose shape products match those lengths, and end exactly at `total_parameter_count`. Any attachment, capacity, layout, shape, dtype, contiguity, or ownership failure produces a controlled worker failure when communication remains possible and closes every attached handle in `finally`; the worker never sends `ready`, and epoch-zero computation cannot begin.

Shared-memory startup validation treats the canonical logical byte length as a minimum-capacity requirement. Each weight or shard-gradient block is accepted when its reported size is greater than or equal to `total_parameter_count × sizeof(float32)` and rejected when smaller. Any platform-allocated capacity beyond that required range remains unused. Every parent and worker NumPy view is limited to the exact canonical offsets, lengths, shapes, and required byte range, so additional page-sized capacity cannot become part of the Transformer numerical state.

Immediately before computing a Logical Training Shard during each epoch, its sole worker writer fills the shard’s complete shared gradient block with `float32` zero and resets its shard loss to `0.0`. It then accumulates only that epoch’s forward-and-backward results. An empty shard reports zero loss and retains an all-zero gradient block. Finite-state validation occurs after shard computation and before the worker reports success. No shard-gradient values may carry forward from an earlier epoch.

Ordered Gradient Reduction uses one reusable parent-local `float32` workspace. At the start of each epoch reduction, the parent fills that workspace with zero and adds the four shard-gradient blocks in canonical order `0 → 1 → 2 → 3` using in-place NumPy addition with no dtype casting. The reduced gradient is not divided by the number of Transformer Training Sequences. Shard losses are accumulated separately in the same canonical order using a Python floating-point accumulator, and only the resulting epoch loss is divided by the total Training Sequence count. The parent verifies the complete reduced gradient, total loss, and epoch loss are finite before permitting the epoch’s Adam update.

Immediately after every Adam update, the parent validates the complete shared weight block and both parent-local Adam moment buffers. Every value must be finite before Generated Text Sample construction or the current Transformer Epoch Update is permitted. A non-finite weight, first moment, or second moment fails the Transformer Training Run at that update boundary, prevents the current sample and epoch event, preserves every prior Saved Transformer Model, prevents final persistence and `done`, and enters guaranteed worker, pipe, shared-memory, and run-slot cleanup.

Adam operates directly over the canonical flat weight, reduced-gradient, first-moment, and second-moment arrays. The two bias-correction scalars are calculated once per inclusive epoch using optimizer step `epoch + 1`. Vectorized NumPy element-wise operations update the persistent `float32` first- and second-moment buffers and then modify the shared flat `float32` weight block. The operation preserves the approved learning rate, beta values, epsilon, unaveraged reduced gradient, canonical parameter layout, and one-update-per-epoch behavior. No nested optimizer state, framework optimizer, parameter regrouping, clipping, averaging, decay, or schedule is introduced. Unrounded optimizer intermediates are covered by the approved tight tolerance-based numerical tests, while resulting public six-decimal values and persisted model values retain exact compatibility checks.

Vectorized Adam uses exactly two reusable parent-local `float64` scratch arrays, each sized to the canonical total parameter count. First-moment arithmetic is completed in `float64` and then stored once into the persistent `float32` first-moment buffer. Second-moment arithmetic is completed in `float64` and then stored once into the persistent `float32` second-moment buffer. Bias correction and the parameter update read those stored `float32` moments, calculate the update in `float64`, and then store the completed result into the shared `float32` weight block. The scratch arrays are never shared with workers and are reused throughout one Transformer Training Run.

Transformer forward and backward operations use an explicit mixed-precision storage contract. Weights, activations, residuals, normalized values, attention matrices, logits, probabilities, forward caches, activation gradients, and parameter gradients are materialized as NumPy `float32` arrays. Means, variances, inverse standard deviations, softmax maxima and sums, dot-product totals, cross-entropy totals, and other scalar reductions use Python `float` or NumPy `float64`. Every completed tensor-producing operation is explicitly written or converted to `float32` before it is cached, returned, shared, or consumed as a later materialized tensor. Optimized NumPy matrix and reduction operations remain permitted, and the implementation does not attempt to reproduce every intermediate TypeScript `Float32Array` write performed inside scalar loops.

Transformer Layer Normalization preserves the reference forward and backward contract. Every token position is normalized independently across the complete embedding dimension using population variance, fixed epsilon `1e-5`, learned `gamma`, and learned `beta`. Forward means, variances, inverse standard deviations, and backward scalar sums are calculated using `float64` reductions. Completed normalized values, cached `xHat` values, outputs, input gradients, gamma gradients, and beta gradients are materialized as `float32`. The implementation uses the reference backward equation and introduces no framework Layer Normalization operation, sample-variance correction, alternative epsilon, or changed normalization scope.

Multi-head causal self-attention preserves the reference forward and backward contract. The fixed 32-feature embedding is split into two contiguous 16-feature heads, and attention scores use scale `1 / sqrt(16) = 0.25`. Query, key, and value projections retain their separate weights and biases. Every query position may attend only to its own position and earlier positions; future score locations are masked before stabilized row-wise softmax and must produce zero probability and zero score gradient. Attention-weighted value vectors are written back into their original head-channel positions, concatenated in channel order, passed through the output projection and bias, and added to the direct residual path. Backpropagation preserves the reference softmax derivative, causal-gradient mask, scaled query and key gradients, value gradients, projection gradients, and direct residual gradient. Materialized arrays remain `float32`, scalar reductions follow the approved `float64` boundary, and hidden unrounded values use the approved tight tolerance-based comparisons.

Every Transformer block preserves the reference position-wise feed-forward and second-residual contract. The second Layer Normalization output is projected from embedding dimension `32` to feed-forward dimension `128`, receives its established bias, passes through element-wise ReLU, is projected back from `128` to `32`, receives the second projection bias, and is added to the attention-residual value `x1`. Backpropagation adds the direct second-residual gradient to the normalized feed-forward-path gradient, uses a ReLU derivative of one only where the stored first-projection value is strictly greater than zero, and accumulates the complete `ff1W`, `ff1B`, `ff2W`, and `ff2B` gradients. No GELU, SiLU, gating, dropout, fused framework MLP, or changed residual placement is introduced.

The final Transformer output boundary preserves the reference formulas. The last block output passes through final Layer Normalization using `lnFGamma` and `lnFBeta`, then through the learned Vocabulary projection `headW` and `headB`, followed by stabilized row-wise softmax. Cross-entropy is the average across sequence positions of `-log(target_probability + 1e-10)`. Backpropagation begins with a materialized `float32` logits gradient equal to probability divided by sequence length, with `1 / sequence_length` subtracted from each correct target entry. The implementation then accumulates the output-head bias and weight gradients, propagates through `headW`, and applies the approved final Layer Normalization backward contract. It introduces no weight tying, label smoothing, alternative loss reduction, fused framework loss, or changed numerical safeguard.

Transformer input construction preserves separate learned token and absolute positional embeddings. For each sequence position, the input activation is the `float32` sum of the Vocabulary row selected from `tokEmb` and the corresponding position row from `posEmb`. After backpropagating through every Transformer block, each position’s input gradient is accumulated into both parameter tables. Repeated token IDs contribute independently to the same token-embedding row; Python must use an unbuffered repeated-index accumulation such as `numpy.add.at()` or an explicitly ordered equivalent rather than buffered advanced-indexed addition. Positional gradients accumulate into their matching absolute rows. No sinusoidal, rotary, relative, tied, or fused embedding representation is introduced.

Transformer Weight Initialization uses a dedicated traversal that is independent of the canonical flat shared-memory layout. One request-owned Mulberry32 generator begins at seed `42`. Blocks are initialized in ascending layer order; within each block, random matrices are initialized in the exact order `wQ`, `wK`, `wV`, `wO`, `ff1W`, and `ff2W`. After all blocks, initialization continues with `tokEmb`, `posEmb`, and `headW`. Every Xavier matrix uses limit `sqrt(6 / (fan_in + fan_out))`, consumes exactly one Mulberry32 value per coordinate, and stores each completed coordinate immediately as `float32`. Bias arrays and beta arrays are filled with zero, Layer Normalization gamma arrays are filled with one, and those deterministic fills consume no random values. Initialization must not simply traverse the canonical packed-memory layout because doing so would change random consumption and every initial matrix.

Each Xavier-initialized Transformer matrix is filled one coordinate at a time in explicit C-order. Initialization traverses row zero from left to right, followed by each subsequent row in order, consumes exactly one request-owned Mulberry32 value for each coordinate, applies the established Xavier formula, and immediately stores the completed coordinate as `float32`. NumPy-native or Python-native random generation, bulk random-array construction, alternate traversal orders, and extra discarded random draws are prohibited at this initialization boundary.

All Transformer randomness uses one exact JavaScript-compatible Mulberry32 algorithm. Generator state is stored as an unsigned 32-bit integer; state addition and multiplication results are explicitly masked with `0xFFFFFFFF`; right shifts reproduce JavaScript zero-filling unsigned behavior; and each output is the final unsigned 32-bit value divided by `2³²`. Weight initialization uses one request-owned stream seeded with `42`. Every Generated Text Sample uses a separate request-owned stream seeded with `(42 + epoch) modulo 2³²`. Python’s `random` module, NumPy random generators, unbounded Python integer arithmetic without the required masks, and module-global mutable generator state are prohibited at these compatibility boundaries.

The exact JavaScript-compatible `Mulberry32` implementation and its unsigned 32-bit constants are owned by `ml/math_utils.py` as a shared numerical primitive. Word2Vec imports the unchanged class into its own module namespace so the established `how_llms_work.ml.word2vec.Mulberry32` import remains valid, while Transformer code imports the class directly from `ml.math_utils`. The project maintains only one production Mulberry32 implementation; Word2Vec and Transformer may not duplicate, subclass, wrap, or alter its arithmetic. Existing exact Word2Vec random-sequence, wraparound, draw-count, initialization, shuffle, and sampling tests remain regression requirements, and focused shared-utility tests verify that both learning demos use the same class object.

The project’s TypeScript-compatible decimal rounding operation is owned by `ml/math_utils.py` as one shared finite-number primitive. `round_typescript_decimal(value, digits)` preserves the established non-negative digit validation, finite-input and finite-scaled-value enforcement, JavaScript-compatible half-tie behavior, and signed-zero normalization. Word2Vec imports and re-exports the shared helper and retains `round_embedding_loss()` as its established wrapper. XOR retains `round_like_typescript()` with its existing name and signature but delegates to the shared helper. Transformer code imports the shared helper directly. The three Learning Demos may not maintain independent rounding implementations or use Python’s built-in `round()` at TypeScript-compatible public or persistence boundaries.

`ml/matrix.py` is a stateless numerical-primitive module rather than a model or training subsystem. It contains only narrowly reusable, independently tested, shape-checked NumPy operations needed by Transformer forward and backward calculations, including matrix products, transposed matrix products, in-place bias and residual addition, column reduction, and stabilized row-wise softmax. It owns no mutable state, randomness, Xavier initialization, Transformer configuration, model parameters, caches, attention or normalization architecture, backpropagation orchestration, Adam state, shared-memory lifecycle, worker protocol, route behavior, SSE construction, or persistence. Higher-level Transformer formulas and ownership remain in `ml/transformer.py`, while shared random and rounding primitives remain in `ml/math_utils.py`.

Every `ml/matrix.py` primitive enforces its documented tensor contract before numerical work begins. Inputs must be NumPy arrays with exact `float32` dtype, expected rank and dimensions, and C-contiguous storage. In-place destinations must additionally be writeable and have the exact required shape. Matrix primitives do not silently cast, reshape, broadcast, copy, or repair incompatible inputs. Row-bias addition permits only its explicitly documented `(M, N)` plus `(N,)` operation; all other element-wise operations require equal shapes. A dtype, rank, shape, contiguity, writeability, finiteness, or unsupported-broadcasting defect fails at the primitive boundary rather than propagating into later Transformer activations or gradients.

`stable_row_softmax()` accepts only rank-two, C-contiguous `float32` arrays containing finite values or intentional negative-infinity causal-mask entries. It rejects NaN, positive infinity, and any row without at least one finite value. For each row, the helper calculates the maximum finite score, shifted exponentials, and normalization sum using `float64`; requires a finite positive sum; and materializes the completed probability row as `float32`. Intentional negative-infinity entries must produce exactly `0.0` probability. The helper never substitutes a uniform distribution, repairs invalid values with `nan_to_num()`, or permits an all-masked row.

`stable_row_softmax()` is a pure allocating operation. It leaves its validated score input unchanged and returns a separate, newly allocated, writeable, C-contiguous `float32` probability array with exactly the same shape. Input-output aliasing is prohibited, including partial overlap through views or shared backing storage. Focused tests preserve a copy of the original scores, require exact input equality after the call, and verify that the score and probability arrays share no memory.

All allocating `ml/matrix.py` primitives are pure with respect to their inputs. Matrix products, transposed matrix products, column reductions, and stabilized row-wise softmax return newly allocated, writeable, C-contiguous `float32` arrays with the exact documented output shape. Their outputs share no memory with any input, and every input remains unchanged. Mutation is permitted only through helpers whose names explicitly end in `_in_place`; those helpers modify only their documented destination argument. This ownership boundary prevents numerical primitives from destroying forward caches, residual inputs, shared read-only weight views, or tensors needed by later backward operations.

The mutating `add_bias_in_place()` and `add_in_place()` primitives require complete source–destination memory separation. They reject identical arrays, overlapping views, partial overlap, and any other shared backing elements before mutation begins. The destination must be a writeable, C-contiguous `float32` array with the exact documented shape; the source must be a separate C-contiguous `float32` array with its exact documented shape and may be read-only. Row-bias addition permits only the established `(M, N)` destination plus `(N,)` bias contract, while ordinary in-place addition requires identical source and destination shapes. After validation, addition writes only to the destination with no dtype casting or implicit repair.

`sum_columns()` preserves the approved mixed-precision reduction boundary. It accepts one validated, finite, rank-two, C-contiguous `float32` input; calculates its axis-zero column totals using an explicit `float64` accumulator; and stores the completed totals exactly once in a newly allocated, writeable, C-contiguous `float32` output. The output has shape equal to the input column count, shares no memory with the input, and must remain finite after `float32` storage. The input remains unchanged. The helper does not use default `float32` accumulation, repeated intermediate `float32` stores, an output alias, or a caller-provided destination.

The allocating `matmul()`, `matmul_transpose_b()`, and `matmul_transpose_a()` primitives calculate their dot products using explicit `float64` arithmetic and then materialize the completed matrix exactly once as a newly allocated, writeable, C-contiguous `float32` array. They accept only validated rank-two, C-contiguous `float32` inputs with exact compatible dimensions; leave every input unchanged; prohibit batch broadcasting, rank promotion, dtype coercion, and input-output memory overlap; and require the stored `float32` result to remain finite. Unrounded matrix-product values use the approved tight tolerance-based numerical tests rather than bit-for-bit TypeScript scalar-loop comparisons.

The mutating `add_bias_in_place()` and `add_in_place()` primitives preserve the approved arithmetic-versus-storage boundary. After validating dtype, shape, C-contiguity, writeability, and complete source–destination memory separation, each helper reads the stored `float32` operands, calculates the complete element-wise addition using explicit `float64` arithmetic, and stores the completed result into the existing `float32` destination. Row-bias addition permits only the established `(M, N)` destination plus `(N,)` bias operation. The helpers do not perform implicit `float32` arithmetic, unsupported broadcasting, dtype promotion, or overlapping in-place ufunc execution.

The mutating `add_bias_in_place()` and `add_in_place()` primitives use a transactional numerical commit boundary. After all dtype, shape, contiguity, writeability, broadcasting, and memory-separation checks succeed, the helper calculates the complete result in a separate `float64` array, converts it into a separate C-contiguous `float32` candidate, and validates every stored candidate value as finite. Only a fully valid candidate is copied into the destination. Any validation, arithmetic, conversion, allocation, overflow, NaN, or infinity failure raises before the destination is modified. Tests preserve an exact copy of the destination and prove that every failing path leaves it unchanged.

All actual workers must complete startup within one shared 30-second deadline measured with `time.monotonic()`. The deadline begins after the parent has started the complete Request-Scoped Worker Group and is not restarted separately for individual workers. During startup, the parent observes worker pipes and process sentinels through the approved `0.1`-second polling loop, checks browser disconnection after each poll, and accepts only fully validated `ready` messages from expected workers. An early worker exit, controlled worker failure, malformed or duplicate readiness message, unexpected protocol message, browser disconnection, or expiration of the shared deadline fails the Transformer Training Run before epoch zero and enters bounded cleanup. A startup failure cannot persist a model or emit `done`.

Every epoch’s complete four-shard worker computation has one shared five-minute deadline measured with `time.monotonic()`. The deadline begins only after all epoch `compute` messages have been sent and is not restarted for individual workers, messages, or Logical Training Shards. During the deadline, the parent uses the established `0.1`-second polling loop to observe worker pipes and process sentinels, validate results, and check browser disconnection. An unexpected worker exit, controlled worker failure, malformed or incomplete result set, browser disconnection, or deadline expiration fails the Transformer Training Run before Ordered Gradient Reduction or Adam. An epoch timeout cannot generate a sample, emit that epoch, persist a model, or emit `done`; it enters bounded worker and shared-memory cleanup.

Every individual Generated Text Sample has one five-minute deadline measured with `time.monotonic()`. The deadline begins when that sample’s parent-owned generation operation starts and applies to the complete sample, not separately to individual generated tokens. The async route observes completion at the established `0.1`-second polling boundary. A browser disconnect, route cancellation, or deadline expiration sets the request-owned `threading.Event`, causing generation to finish any already-started forward pass but stop before beginning another token. The route waits for the generation helper to return before releasing numerical storage that the thread could still access. A timed-out or cancelled sample fails the Transformer Training Run, prevents the associated `epoch` event, preserves prior persisted models, prevents final persistence and `done`, and enters guaranteed worker, shared-memory, and run-slot cleanup.

Final post-training loss evaluation has one five-minute deadline measured with `time.monotonic()`. The deadline begins when the parent-owned final evaluation starts through `asyncio.to_thread()` and applies to the complete evaluation across all Transformer Training Sequences. The async route observes completion at the established `0.1`-second polling boundary. A browser disconnect, route cancellation, or deadline expiration sets the request-owned `threading.Event`; the evaluation may complete one already-started forward pass but must stop before beginning another Training Sequence. The route waits for the evaluation helper to return before releasing shared numerical storage. A timed-out or cancelled final evaluation produces no Saved Transformer Model and no `done` event, preserves the previous configuration-specific model, and enters guaranteed worker, shared-memory, and run-slot cleanup.

`POST /train-transformer` reuses the existing shared `format_sse()` and `create_sse_response()` functions without modification or duplication. The route formats only the approved `init`, `epoch`, and `done` events through the shared formatter and returns its async event iterator through the shared response factory. Phase 5 introduces no Transformer-specific framing, media type, headers, event IDs, retry fields, comments, heartbeat messages, or alternate JSON transport. The Transformer route owns event selection, ordering, payload construction, presentation timing, disconnect handling, and lifecycle orchestration, while `sse.py` remains the sole authority for wire framing and shared streaming-response headers.

Phase 5 enforces explicit module ownership. `ml/math_utils.py` owns the shared Mulberry32 and TypeScript-compatible rounding primitives. `ml/matrix.py` owns only stateless, validated NumPy tensor operations. `ml/transformer.py` owns immutable preprocessing, canonical parameter layout, initialization, forward and backward mathematics, Adam, Generated Text Sample construction, final evaluation, and Saved Transformer Model construction. `ml/transformer_worker.py` owns the importable spawned-process entry point, typed worker protocol, shared-memory attachment and validation, shard computation, and Request-Scoped Worker Group supervision. `routes/train_transformer.py` owns request validation integration, active-run reservation, SSE orchestration, disconnect and cancellation handling, presentation delay, final persistence, logging, and quiet post-stream failure handling. `main.py` only imports and registers the completed router. Numerical formulas may not be implemented in the route, and worker code may not construct SSE events or persist model files.

Every worker startup record and parent-worker control message is represented by a dedicated top-level `@dataclass(frozen=True, slots=True)` defined in `ml/transformer_worker.py`. The protocol defines separate `WorkerStartupConfig`, `ReadyMessage`, `ComputeMessage`, `ResultMessage`, `FailureMessage`, `StopMessage`, and `StoppedMessage` classes. Their fields contain only explicitly validated primitive values, strings, and immutable tuples; they never contain NumPy arrays, shared-memory buffers, locks, FastAPI objects, generators, request objects, exceptions, or tracebacks. Numerical arrays remain in shared memory. The receiver validates the exact message class and every field before acting, and any unknown class or invalid field is a protocol failure. SSE payload dictionaries exist only at the route boundary.

Every spawned Transformer worker permits exactly one outstanding `ComputeMessage`. Worker execution follows the explicit states `STARTING → READY → COMPUTING → READY → STOPPING → STOPPED`. A worker accepts a compute command only while `READY`, processes all shards assigned by that command in ascending shard order, sends exactly one corresponding `ResultMessage`, and returns to `READY`. The parent may not dispatch the next epoch until every current-epoch result has been validated, Ordered Gradient Reduction and Adam have completed, the updated numerical state has been validated, and the current Generated Text Sample has finished. Epoch pipelining, queued compute commands, concurrent pipe access, gradient-buffer overwrite, and worker reads during parent weight mutation are prohibited. An invalid state transition, unsolicited result, duplicate command, or result received without one outstanding computation fails the Transformer Training Run.

Each worker publishes one atomic application-level result for each accepted `ComputeMessage`. It first zeroes and completely computes every assigned Logical Training Shard in ascending shard order, then validates all assigned shard losses and complete gradient blocks. Only after all assigned numerical results are valid does it send exactly one `ResultMessage`; that accepted message is the parent’s commit marker for reading those shared gradient blocks. Workers never publish successful partial-shard results. A computation that fails after partially modifying a gradient block sends no successful result, and all partial numerical state is ignored and discarded with the failed Transformer Training Run. The parent performs Ordered Gradient Reduction only after all four Logical Training Shards have been committed exactly once for the current epoch.

Worker failures are sanitized before crossing the process boundary. A worker records the complete internal exception through its module-level logger while inside the applicable exception handler, then sends a `FailureMessage` only when its pipe remains usable. That message contains only the worker index, stable phase, stable failure code, optional current epoch, and applicable Logical Training Shard IDs. It never contains raw exception text, exception objects, traceback data, filesystem paths, shared-memory names, model parameters, gradients, losses, generated text, or other numerical state. The parent logs only the stable code and limited protocol context, fails the Transformer Training Run, and never forwards worker-failure information through SSE. Every worker closes its attached shared-memory handles in `finally` regardless of whether a failure message can be sent.

Worker process exit status is an independent lifecycle signal in addition to the typed pipe protocol. A worker that receives `StopMessage`, sends `StoppedMessage`, and completes cleanup returns normally with exit status `0`. A worker that detects a startup, compute, protocol, numerical, or shutdown failure logs the full internal exception, attempts to send one sanitized `FailureMessage`, closes its attached shared-memory and pipe handles in `finally`, and terminates with `SystemExit(1)`. A controlled `FailureMessage` followed by exit status `1` is an expected failed-worker sequence. A nonzero exit without a failure message is an unexpected worker failure. Exit status `0` before a valid `StoppedMessage`, or a `StoppedMessage` followed by nonzero exit status, is a protocol failure. No failed-worker exit may be followed by gradient reduction, persistence, or `done`.

The parent-worker control protocol has fixed version `1`. Every startup and control record contains `protocol_version`, and every worker-originated record also contains `worker_index`. Receivers require exact ordinary-integer fields, reject Boolean substitutes, require the protocol version to equal the supported constant, and verify that each reported worker index matches the process and dedicated pipe from which the message arrived. Phase 5 performs no protocol-version negotiation, downgrade, fallback, or best-effort interpretation. A missing, unknown, mismatched, malformed, or incorrectly typed version or worker identity fails the Transformer Training Run before the message can affect shared numerical state.

Each worker pipe has exactly one active endpoint owner in each process. The parent creates the duplex `parent_connection` and `worker_connection`, passes the worker endpoint through the spawned process configuration, and closes its own copy of that worker endpoint immediately after `Process.start()` succeeds. The parent thereafter uses only `parent_connection`; the worker uses only `worker_connection` and closes it in its guaranteed cleanup boundary. After the worker exits and is joined, the parent closes its remaining endpoint. If process startup fails, the parent closes both endpoints because no child successfully assumed ownership. Unused duplicate endpoints may not remain open because they can delay pipe-closure and EOF detection.

Transformer cleanup is non-short-circuiting and preserves the request’s original outcome. The cleanup boundary sets cooperative cancellation, completes bounded worker shutdown, joins workers, records exit codes, closes parent pipe endpoints, closes eligible Process objects, releases NumPy and memoryview references, closes parent SharedMemory handles, and attempts each parent-owned unlink independently. Every cleanup operation has guarded internal logging, and one cleanup failure cannot skip later cleanup actions. An original `asyncio.CancelledError` is re-raised after cleanup. An original training or streaming failure remains the primary outcome rather than being replaced by a secondary cleanup failure. The process-local Transformer run lock is released in the outermost and final cleanup boundary so no pipe, process, shared-memory, or unlink defect can permanently cause later valid requests to receive HTTP `429`.

The Transformer request treats `temperature` and `topP` as strict finite JSON numbers rather than strict floating-point-only values. A shared `BeforeValidator` accepts only values whose exact Python type is `int` or `float`, explicitly rejects Boolean values and every other type, converts the accepted value to `float`, and requires the result to be finite before normal field-bound validation. This permits valid JSON values such as `1` and `0.8` while rejecting `"1"`, `"0.8"`, `true`, NaN, and positive or negative infinity. `epochs`, `numLayers`, and `maxTokens` remain strict bounded integers.

Phase 5 verification uses layered pytest coverage. Exact unit fixtures verify shared numerical helpers, immutable preprocessing, Vocabulary and sequence construction, shard boundaries, canonical parameter layouts, deterministic initialization and sampling, reporting schedules, public rounding, SSE field sets, and deterministic serialization. Tight tolerance-based fixtures independently verify unrounded forward, backward, attention, normalization, feed-forward, loss, gradient, Adam, and final-evaluation calculations. Focused integration tests use the real `"spawn"` multiprocessing context, real duplex pipes, real shared-memory blocks, and one-through-four actual workers to verify protocol behavior, deterministic Ordered Gradient Reduction, worker-count independence, failures, timeouts, cancellation, and cleanup. Route tests replace expensive numerical and process operations only through explicit injection seams or narrow monkeypatches and verify HTTP `422`, `429`, and sanitized `500` responses, exact SSE order and payload fields, persistence-before-`done`, quiet post-stream failures, disconnection handling, and guaranteed run-lock release. Persistence tests use pytest’s isolated `tmp_path` directories. Expected values must be independently calculated or captured from the TypeScript reference and may not be produced by the production Python helper under test.

The ordinary `poetry run pytest` suite includes small, bounded integration tests using the real `"spawn"` multiprocessing context, importable worker entry point, pickled startup records, spawned processes, duplex pipes, process sentinels, and request-scoped shared-memory blocks. These tests verify successful startup, one real shard computation, one-through-four-worker execution, worker-count-independent reduction, cooperative shutdown, controlled failure, nonzero exits, shortened timeout seams, and complete resource cleanup. They are not skipped on supported development platforms. Maximum-configuration endurance runs are separately registered as slow or manual smoke tests and are not required for the ordinary correctness suite.
