# Ticket 012: Centralize TypeScript-compatible randomness and rounding

## What to build

Provide one shared deterministic utility boundary for all Python Backend learning demos that need JavaScript-compatible random streams or decimal rounding. Move the established Mulberry32 behavior and TypeScript-compatible public rounding into the shared utility boundary while preserving every existing Word2Vec and XOR compatibility wrapper.

The new boundary must be usable by Transformer Weight Initialization and every Sample Random Stream without allowing one run or one generated sample to consume another stream's state. Existing completed Learning Demos must continue producing their established public behavior.

## Acceptance Criteria

- [ ] The shared Mulberry32 implementation reproduces independently captured JavaScript reference outputs for representative seeds, including seed `42`, zero, maximum unsigned 32-bit input, and wraparound cases.
- [ ] Mulberry32 state is normalized modulo `2^32`, and each call consumes exactly one draw with the established JavaScript-compatible bit operations.
- [ ] Two generators created from the same seed produce identical sequences while advancing independently.
- [ ] Separate generators used for Weight Initialization and Generated Text Samples cannot change one another's draw counts or outputs.
- [ ] The shared decimal-rounding operation reproduces the approved TypeScript behavior at ordinary values, positive and negative half ties, values beyond six decimals, very small magnitudes, and signed zero.
- [ ] Public six-decimal rounding normalizes negative zero to positive `0.0` where the Saved Transformer Model contract requires it.
- [ ] Non-finite inputs are rejected before they can become public values or persisted model coordinates.
- [ ] Word2Vec re-exports the same shared Mulberry32 implementation rather than maintaining a second implementation.
- [ ] Existing Word2Vec random sequences, training fixtures, and rounded public outputs remain unchanged.
- [ ] Existing XOR rounding wrapper names remain available and retain their established observable behavior.
- [ ] Expected random sequences and rounding outputs are fixed independent evidence and are not generated by calling the production operation under test.
- [ ] Sequential and concurrent utility use does not share mutable generator state unless the same generator instance is deliberately passed by the caller.

## Testing Expectations

- **Approved test seam:** The stable public deterministic-utility boundary used by existing learning demos and the Transformer module.
- **Behavior to verify:** Mulberry32 streams, unsigned wraparound, exact draw consumption, independent stream ownership, TypeScript-compatible decimal rounding, signed-zero normalization, non-finite rejection, and regressions for Word2Vec and XOR wrappers.
- **Relevant prior art:** The completed deterministic Word2Vec and XOR fixtures, plus the Phase 5 exact random-stream and public-rounding policy.
- **Do not test through:** Private bit-operation helper names, local variable names, a particular class storage layout, or Python's built-in `random` internals.

## Blocked By

- None — can start immediately.

## Constraints and Out of Scope

- Use one shared implementation; do not copy Mulberry32 or rounding logic into Transformer-specific code.
- Do not use NumPy-native randomness, Python's `random` module, cryptographic randomness, or a third-party PRNG.
- Do not change existing public Word2Vec or XOR results merely to simplify the shared utility.
- Do not add seed controls to any HTTP request.
- Do not implement Transformer preprocessing, matrix operations, model mathematics, workers, routing, or persistence in this ticket.
- No new dependency or lockfile change is expected.
